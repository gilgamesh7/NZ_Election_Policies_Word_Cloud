# Implementation Plan

**Project:** NZ Political Policy Word Cloud  
**Status:** Proposed phased plan  
**Principle:** Deliver a tested vertical slice at each phase; do not build the whole application in one prompt.

## Phase 0 — Review and agree the specification

**Purpose:** Resolve requirements before code generation.

Tasks:
- Review `.agent/REQUIREMENTS.md` and `AGENTS.md`.
- Confirm how a party's allowed hostnames are represented.
- Confirm whether a party can have multiple starting URLs and how those pages are grouped into one corpus.
- Agree the default exclusions for obvious non-policy pages.
- Confirm whether frequency and TF-IDF clouds should both be generated by default.

Exit criteria:
- User approves the requirements.
- Any unresolved assumptions are documented.
- No application code is written in this phase.

## Phase 1 — Project skeleton and environment

**Purpose:** Establish a reproducible Python workspace.

Tasks:
- Create the package and notebook directory structure.
- Add project metadata and a dependency strategy.
- Document virtual-environment creation and dependency installation.
- Add a minimal test configuration and `pytest` setup.
- Add a configuration example that does not invent real party URLs.

Tests/checks:
- Environment setup works on the user's Mac.
- Test runner starts successfully.
- Notebook opens and imports the project package.

Exit criteria:
- Clean project structure exists.
- Setup steps are documented and reproducible.
- Baseline checks pass.

## Phase 2 — Configuration and URL rules

**Purpose:** Validate inputs and make crawl scope predictable before network access.

Tasks:
- Define the party configuration schema.
- Validate party IDs, names, URL syntax, and allowed hostnames.
- Implement URL resolution and normalisation.
- Implement same-host checks, supported-scheme checks, and exclusion rules.
- Record reasons when links are rejected.

Tests:
- Valid and invalid configuration.
- Relative and absolute URLs.
- Fragment removal and duplicate detection.
- External host and unapproved subdomain rejection.
- `mailto:`, `tel:`, JavaScript, and unsupported file links.
- Query parameters are not blindly removed.

Exit criteria:
- Configuration validation and URL filtering work entirely offline.
- Invalid configuration fails clearly before any request is made.

## Phase 3 — First-level HTML crawler

**Purpose:** Fetch starting pages and their eligible direct links without recursion.

Tasks:
- Add HTTP fetching with user-agent, timeouts, size limits, polite delays, and restrained retries.
- Discover links only on starting pages.
- Enforce same-domain and configured exclusions.
- Deduplicate pages per party.
- Record page status, final URL, timestamps, skips, and failures.
- Treat retrieved page content as untrusted data.

Tests:
- Local HTML fixtures and mocked HTTP responses.
- Starting-page links are fetched.
- Links found on first-level pages are not followed.
- Same-domain and duplicate rules hold.
- Redirects, timeouts, HTTP errors, and invalid content types are handled.
- A failed page does not stop the run.

Exit criteria:
- Crawl manifest is accurate and the crawler never exceeds one link level.

## Phase 4 — HTML text extraction and source records

**Purpose:** Produce inspectable text linked to its origin.

Tasks:
- Extract main content using the selected extraction library.
- Add a documented fallback for failed extraction.
- Preserve headings, paragraphs, and meaningful lists where possible.
- Store source URL and extraction status with every record.
- Save extracted text without overwriting it with cleaned text.
- Report empty or suspiciously short extractions.

Tests:
- Saved fixtures with menus, footers, headings, paragraphs, lists, and boilerplate.
- Malformed HTML and empty content.
- Extraction fallback and failure reporting.
- Source URL remains attached to each text record.

Exit criteria:
- The user can inspect extracted text and identify its source.
- Failed extraction is visible rather than silently accepted.

## Phase 5 — Text cleaning and frequency analysis

**Purpose:** Establish the first useful analytical result.

Tasks:
- Normalise whitespace and Unicode.
- Implement documented tokenisation.
- Apply a standard English stop-word list and project-specific configurable exclusions.
- Count terms per party and rank them deterministically.
- Export the full frequency table and top-20 list.
- Keep stop-word exclusions transparent and editable.

Tests:
- Common filler words are removed.
- Meaningful terms are retained unless explicitly excluded.
- Counts and ranks are correct.
- Tie-breaking is deterministic.
- Fewer than 20 terms is handled without padding.

Exit criteria:
- Frequency CSV is correct for known test text.

## Phase 6 — TF-IDF analysis

**Purpose:** Add a comparative ranking distinct from raw frequency.

Tasks:
- Aggregate eligible text into one corpus document per party.
- Fit TF-IDF over the party documents included in a run.
- Export scores and ranks with documented settings.
- Handle empty and very small corpora.
- Explain that results change when the included party set changes.

Tests:
- Terms that are relatively distinctive receive appropriate higher scores in a controlled fixture.
- Empty documents and insufficient vocabulary are handled.
- Output order and tie-breaking are deterministic.
- The implementation does not present TF-IDF as an objective measure of policy importance.

Exit criteria:
- TF-IDF CSV is produced and interpretation limits are documented.

## Phase 7 — Word clouds and output management

**Purpose:** Produce the selected visual outputs.

Tasks:
- Generate frequency and TF-IDF PNG clouds per party.
- Use consistent dimensions and readable defaults.
- Use clear filenames identifying party and ranking method.
- Save CSVs, text records, page manifest, and run metadata in a run-specific output directory.
- Handle empty results without misleading images.

Tests:
- Expected files are generated for non-empty fixtures.
- Output filenames are safe and deterministic within a run.
- Existing run output is not accidentally overwritten.
- Empty data produces a useful warning.

Exit criteria:
- A fixture run produces inspectable PNG, CSV, text, and metadata outputs.

## Phase 8 — Notebook integration

**Purpose:** Make the complete workflow usable by the project owner.

Notebook sections:
1. Overview and limitations.
2. Load and validate configuration.
3. Run collection.
4. Review page status and errors.
5. Inspect sample extracted text.
6. Clean and analyse text.
7. Display and save word clouds.
8. Summarise output paths and known limitations.

Tasks:
- Keep logic in the package and orchestration in the notebook.
- Add progress and concise status summaries.
- Ensure repeated cell execution does not duplicate records.
- Include troubleshooting notes.

Checks:
- Run notebook end-to-end against mocked/local fixtures.
- Manually inspect a small, permitted live-site run when the user supplies URLs.
- Verify all output artefacts and source traceability.

Exit criteria:
- A user can execute the notebook from top to bottom using the documented setup.

## Phase 9 — User acceptance and hardening

**Purpose:** Verify the tool against user-provided websites.

Tasks:
- Start with one party and a small number of URLs.
- Review discovered links and exclusion decisions.
- Manually compare extracted text with the source pages.
- Inspect top terms and stop-word exclusions.
- Add regression fixtures for observed site-specific issues.
- Run against remaining configured parties.
- Document gaps such as JavaScript-rendered content and PDF links.

Exit criteria:
- User accepts the scope and quality of collected text.
- Tests pass.
- Known gaps and collection date are documented.

## Later phase — PDF support

Not part of version 1.

Potential tasks:
- Identify PDF links from eligible pages.
- Fetch permitted PDFs with size and content-type limits.
- Extract text from PDFs with a dedicated library.
- Record page-level extraction metadata and handle scanned/image-only PDFs explicitly.
- Add tests for valid, malformed, empty, and image-only PDFs.

Do not start this phase until the HTML-only version has been accepted.

## Recommended Antigravity workflow

For each phase, ask the agent to:
1. State the intended change and relevant requirements.
2. Propose the smallest design needed.
3. Implement only the approved phase.
4. Add or update tests.
5. Run the relevant tests and show actual results.
6. Summarise changed files, limitations, and any decisions requiring user input.

Do not advance to the next phase while the current phase has failing tests or unresolved behaviour that affects later phases.
